# project-implementation-blueprint.md 差距检查

检查日期：2026-07-02  
对照文件：`project-implementation-blueprint.md`  
最新目标来源：当前讨论形成的“显式灰度验收 + 电脑画面捕捉 + 权限分级 + 人类裁决”的 AI 测试官方向。

## 1. 总体判断

`project-implementation-blueprint.md` 是一个合格的 v1 工程蓝图，已经覆盖了最基础的闭环：

> Git diff / PR 输入 -> 风险清单 -> 分层测试策略 -> 自动执行 -> LLM Judge 报告

但它和最新目标相比，仍有明显差距。差距不在“有没有测试 Agent 的骨架”，而在“有没有形成区别于 Codex/Cursor 测试按钮的产品辨识度”。

当前蓝图覆盖度估计：

- 基础测试 Agent 闭环：约 75%
- 前沿研究痛点对齐：约 55%
- 显式灰度验收：约 20%
- 电脑画面捕捉与可视化复核：约 25%
- 权限分级与安全边界：约 35%
- 人类最终裁决与审计闭环：约 45%
- 整体最新目标覆盖：约 55%-60%

一句话结论：

> 蓝图 v1 能指导做出一个“能跑测试并写报告的 AI 质检工具”，但还不足以指导做出我们现在讨论的“可视化、可接管、可复核、可裁决的 AI 测试官”。

## 2. 最新目标拆解

最新目标可以拆成 10 个可检查要求：

1. `R1_change_understanding`：从 Git diff / PR / 需求中理解变更意图和影响范围。
2. `R2_risk_driven_plan`：生成风险驱动的测试 plan 和详细测试路径。
3. `R3_visible_gray_test`：Agent 接管鼠标键盘，按固定灰度层级显式执行测试。
4. `R4_screen_capture_required`：必须捕捉电脑画面或指定窗口画面，作为测试过程证据。
5. `R5_structured_evidence`：同时采集 DOM、network、console、trace、截图、录屏、断言结果。
6. `R6_permission_model`：参考 Codex / Claude Code 的权限分级，避免 OpenClaw 式泛化接管风险。
7. `R7_human_final_verdict`：最终是否继续、阻塞、提交、接受报告，由用户决定。
8. `R8_conflict_replay`：画面证据与结构化证据冲突时，自动复现并提交用户复核。
9. `R9_failure_policy`：单路径失败后重试，仍失败则记录证据并继续其他路径，最后统一归因。
10. `R10_workbench_ui`：呈现为类似 AI Agent 工作流平台/Cursor 的测试工作台，而不是纯 CLI 或后台脚本。

## 3. 逐项差距检查

| 要求 | 蓝图当前覆盖 | 差距判断 | 需要补充 |
|---|---:|---|---|
| R1 变更理解 | 高 | 已覆盖 diff/PR、改动文件、函数、接口、模块 | 补充需求文档、历史测试、接口契约和证据来源标注 |
| R2 风险驱动测试 plan | 中高 | 已覆盖冒烟、关键路径、异常边界、回归 | 需要输出“详细测试路径”和“预期来源”，不能只输出测试点 |
| R3 显式灰度验收 | 低 | 蓝图有“分层测试策略”，但不是鼠标键盘接管式灰度 | 新增固定灰度层级：smoke/core_path/edge_case/regression |
| R4 电脑画面捕捉 | 低 | 蓝图只提截图、trace，没有桌面/窗口画面捕捉 | 明确作为必选能力：Live View、录屏、鼠标键盘轨迹 |
| R5 结构化证据 | 中 | 已有日志、trace、截图、请求失败信息 | 补齐 DOM、network、console、断言来源、风险覆盖矩阵 |
| R6 权限分级 | 中低 | 蓝图只提安全边界、禁止危险命令 | 增加 observe/browser/workspace/terminal/system 五级权限 |
| R7 人类最终裁决 | 中 | 提到人工 override 和发布建议 | 明确“用户有最终裁决权”，AI 只给建议和证据 |
| R8 证据冲突复现 | 缺失 | 未讨论截图与结构化证据冲突 | 增加冲突处理流程：复现、对比、归因、提交用户 |
| R9 失败后继续策略 | 中 | 提到重试与归因 | 明确单路径失败不终止整轮，重试失败后继续下一个路径 |
| R10 测试工作台 UI | 低 | 蓝图偏 CLI/报告/CI | 新增 Live View、Agent Actions、Evidence Panel 三栏工作台 |

## 4. 最大差距在哪里

### 差距一：蓝图仍偏“自动化测试工具”，而最新目标是“可视化测试官”

蓝图里的执行方式主要是：

- 调用单元测试。
- 调用 API/集成测试。
- 调用 Playwright 冒烟脚本。
- 汇总测试结果。

最新目标要求的是：

- Agent 显式接管鼠标键盘。
- 用户能看到测试过程。
- 每一步都有操作意图、画面证据和结构化证据。
- 用户可在灰度层级之间决定继续或停止。

这会显著改变产品形态：它不应只是 CLI 或 CI 报告，而应是一个测试工作台。

### 差距二：蓝图没有把“电脑画面捕捉”作为一等能力

蓝图提到截图、trace、日志，但这些更像 Playwright 产物。最新目标要求的是桌面/窗口级的画面证据：

- 实时 Live View。
- 鼠标移动、点击、键盘输入。
- 指定窗口截图或录屏。
- 测试结束后给用户提交可复核证据。

这部分是项目展示感和差异化的关键，不能藏在“artifacts”下面。

### 差距三：权限和安全边界还不够产品化

蓝图只在预备知识里提到“禁止危险命令、只读目录、时间/资源预算”。这还不够。

最新目标明确要参考 Codex / Claude Code 的权限分级，同时规避 OpenClaw 式风险。需要把权限设计成产品能力：

- 哪些操作可以自动做。
- 哪些操作需要用户确认。
- 哪些操作默认禁止。
- 哪些操作必须审计。
- 高风险操作如何解释和取消。

### 差距四：LLM Judge 的裁决权需要下放给人

蓝图说“用 LLM Judge 生成结构化报告：真实问题 vs 误报、覆盖缺口、风险评分、是否可发布建议”。这个方向是对的，但表达上容易让评委误解成“AI 自动裁决能不能发布”。

最新目标应改成：

> LLM Judge 负责组织证据、提出风险判断和建议动作；最终裁决权属于用户。

这会让系统更可信，也更符合实际研发流程。

### 差距五：失败策略需要更像测试人员，而不是只像测试运行器

蓝图提到失败归因和重试，但没有规定控制流。

最新目标已经明确：

- 单路径失败先重试。
- 重试仍失败则记录证据。
- 不立即终止整轮测试。
- 继续跑其他路径。
- 最后统一归因，判断是单点问题还是系统性问题。

这个策略很重要，因为它让报告更完整，也更像真实测试人员做回归。

## 5. 对蓝图的更新建议

### 建议一：项目定位改写

原定位：

> 提交前代码变更质检 Agent，输入 diff/PR，输出可追溯风险报告与建议。

建议改成：

> 提交前显式灰度验收 Agent。它从 Git diff/PR 和需求出发，生成风险驱动测试 plan，接管浏览器/鼠标/键盘进行可视化分层验证，捕捉电脑画面和结构化证据，最终把可复核质量报告交给用户裁决。

### 建议二：MVP 目标增加 4 项

在现有 5 项最小可交付后补充：

6. 生成详细测试路径，并按 `smoke -> core_path -> edge_case -> regression` 灰度层级组织。
7. 在 Live View 中可视化执行鼠标、键盘和浏览器操作。
8. 捕捉电脑画面/窗口画面，并与 DOM、network、console、trace 组成证据包。
9. 引入权限分级与人工确认，最终裁决权归用户。

### 建议三：新增系统模块

在原有模块基础上新增：

- `permission-gate`：权限分级、确认弹窗、危险操作拦截、审计日志。
- `visual-gray-runner`：显式灰度执行器，负责编排分层测试路径。
- `screen-capture`：桌面/窗口截图、录屏、鼠标键盘轨迹。
- `evidence-store`：统一保存画面证据、浏览器证据、业务证据和操作日志。
- `conflict-replayer`：证据冲突时自动复现并生成复核包。
- `workbench-ui`：Live View、Agent Actions、Evidence Panel。

### 建议四：里程碑需要重排

原 14-20 天计划偏“先做后端质检工具，再加 Playwright”。如果保留最新目标，建议改成：

1. Day 1-2：固定 Demo 应用、真实 bug、灰度层级、权限边界。
2. Day 3-4：diff 解析和风险计划生成。
3. Day 5-6：可视化测试路径生成与用户确认。
4. Day 7-9：浏览器自动化执行、截图、trace、console、network。
5. Day 10-11：电脑画面捕捉、鼠标键盘操作日志、Live View。
6. Day 12-13：失败重试、继续执行、证据冲突复现。
7. Day 14-15：报告、风险覆盖矩阵、用户最终裁决。
8. Day 16-18：工作台 UI、演示脚本、答辩材料。

### 建议五：验收标准需要升级

原验收标准：

- 至少 1 套 diff 输入能跑完闭环。
- 报告有受影响模块、风险等级、失败归因、覆盖建议。
- 同一输入结果可重复且可追溯。

建议升级为：

- 至少 1 套 diff 能触发真实 bug，并被测试官定位到对应业务路径。
- 测试 plan 必须包含固定灰度层级和详细测试路径。
- Live View 能展示 Agent 的鼠标/键盘/浏览器操作过程。
- 报告必须包含画面证据、结构化证据、操作日志和失败复现步骤。
- 单路径失败后能重试，仍失败后继续执行其他路径。
- 用户可以修改测试 plan，并拥有最终裁决权。
- 高风险操作必须经过权限确认，并写入审计日志。

## 7. 最小版本范围建议

为了避免范围失控，第一版不要做“任意电脑任务接管”，只做：

- 操作一个指定浏览器窗口。
- 操作一个指定本地 Web 应用。
- 读取一个指定项目目录的 diff。
- 运行固定测试命令。
- 捕捉指定窗口画面。
- 对系统级操作一律要求确认。

这样既能展示“像人一样测试”，又不会掉进 OpenClaw 式过宽权限和安全风险里。
