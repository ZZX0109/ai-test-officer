# AI Test Officer 功能测试用例集

## 1. 目的与约定

本用例集基于当前 Workbench、Agent API 与 README 中定义的正式运行链路编写，覆盖项目接入、测试规划、执行、证据、裁决、修复与持续巡检。每个模块均至少包含 3 个正常用例和 3 个极端/异常用例。

- 优先级：`P0` 表示会影响错误放行、数据/源码安全或无法完成主流程；`P1` 表示核心功能受损；`P2` 表示可用性或展示问题。
- 正常用例使用仓库中的 `app-under-test`、`fixtures/todo-lite`、`fixtures/order-portal-lite` 及 `data/scenarios` 的场景数据。
- 极端用例须保留 Run ID、事件流、日志、截图、DOM、网络记录和 Artifact 校验结果；不可仅以页面提示作为通过依据。
- 除明确标记为“需真实环境”的用例外，均可在本地开发配置和测试替身中执行。

## 2. 测试环境与基线

| 编号 | 前置条件 | 期望 |
| --- | --- | --- |
| ENV-01 | Node 版本满足 `package.json` 的 `>=22.5.0`，依赖已安装 | Workbench、Agent 与被测演示应用可启动；记录版本、提交 SHA、配置摘要。 |
| ENV-02 | 准备无登录项目、需登录项目、含 OpenAPI 项目及启动失败项目 | 各项目均能在项目列表中独立保存和选择。 |
| ENV-03 | 准备有效、失效、无权限三类模型/项目凭据 | 测试中不记录明文密码、API Key 或 Authorization 请求头。 |
| ENV-04 | 准备可篡改 Artifact 副本、断网/慢网和已停止运行时 | 能重复验证完整性、恢复、超时和错误分流。 |

## 4. 沙盒、缓存与运行时生命周期

| ID | 类型 | 优先级 | 步骤 | 预期结果 |
| --- | --- | --- | --- | --- |
| RT-01 | 正常 | P0 | 首次运行一个 Node 项目，再以未改动源码重复运行 | 首次安装依赖；第二次命中同项目依赖缓存并复用，但仍使用隔离运行环境。 |
| RT-02 | 正常 | P1 | 仅修改业务源码后重启项目 | 刷新源码而复用依赖；新页面内容可见且运行时版本/事件已更新。 |
| RT-03 | 正常 | P1 | 在运行中执行暂停、恢复、取消、停止 | 状态机顺序合法，SSE 和轮询最终一致，取消后不再继续产生执行步骤。 |
| RT-04 | 极端 | P0 | 被测启动脚本尝试 `open`、读取 SSH/云凭据或访问 Docker socket | 行为被拦截或无可用挂载；日志记录拒绝原因，不弹出外部浏览器。 |
| RT-05 | 极端 | P0 | 模拟 CPU、内存、PID、日志或产物额度耗尽 | 运行被有界终止并归类为环境/资源问题；已采集证据仍能提交，不能误判 pass。 |
| RT-06 | 极端 | P0 | Agent 重启后查询先前受管运行时，再停止该项目 | 可恢复发现并接管实际运行时；停止会终止真实进程/容器而不只是更新 UI。 |

## 5. 凭据、安全与权限

| ID | 类型 | 优先级 | 步骤 | 预期结果 |
| --- | --- | --- | --- | --- |
| SEC-01 | 正常 | P0 | 创建模型凭据并设为默认，执行连接测试 | 凭据可用、列表只显示掩码，最后使用时间正确更新。 |
| SEC-02 | 正常 | P0 | 为项目保存登录账号/密码，执行需登录的规划和场景 | 凭据在运行时注入，登录可完成；页面、事件、报告均不回显密钥。 |
| SEC-03 | 正常 | P1 | 创建只读/浏览器操作/修复写入等不同授权，再开始运行 | 运行仅请求所需 capability，授权范围与项目、Run 绑定。 |
| SEC-04 | 极端 | P0 | 使用失效 API Key、错误项目账号或无 scope 的 token | 测试失败可定位为认证/授权，密钥不泄露，不自动切换到另一项目凭据。 |
| SEC-05 | 极端 | P0 | 在未授权时触发浏览器控制、联网安装、沙盒写入或宿主应用 | 产生可恢复 interrupt；操作未发生，批准后仅继续被批准的动作。 |
| SEC-06 | 极端 | P0 | 轮换或删除正被运行引用的凭据 | 已开始的 Run 按明确策略继续或安全失败；新请求不能再使用旧凭据，审计记录完整。 |

## 8. Run 编排、审批与控制

| ID | 类型 | 优先级 | 步骤 | 预期结果 |
| --- | --- | --- | --- | --- |
| RUN-01 | 正常 | P0 | 确认计划、批准 Run 计划、授予所需权限 | Parent Run 创建一次，进入正确状态；每条可执行路径创建对应 child run。 |
| RUN-02 | 正常 | P0 | 多路径运行中让一条独立路径失败 | 其他独立路径继续；父 Run 等待所有 CoverageItem 有明确处置再聚合。 |
| RUN-03 | 正常 | P1 | 用 SSE 订阅运行，同时刷新页面并通过轮询恢复 | 同一 runId 的版本、事件和执行进度不回退、不重复；刷新后可恢复展示。 |
| RUN-04 | 极端 | P0 | 重复点击批准/授权，或以旧 `expectedVersion` 提交 | 幂等键/乐观锁生效；不重复入队、重复调用模型或重复提交 Artifact。 |
| RUN-05 | 极端 | P0 | 在 approval、credential、network、repair 等 interrupt 上暂停后重启服务 | 可从同一 thread/run 恢复，用户决策只影响指定 interrupt。 |
| RUN-06 | 极端 | P0 | 并发暂停、恢复、取消同一 Run，或取消正在执行的 child run | 不出现非法状态回跳；最终事件可解释，取消后不得生成成功 finalStatus。 |

## 10. Artifact、证明链与可信裁决

| ID | 类型 | 优先级 | 步骤 | 预期结果 |
| --- | --- | --- | --- | --- |
| EV-01 | 正常 | P0 | 成功场景完成后打开证据面板和结论证明 | Conclusion 可逐级追溯至 Assertion、Evidence、Artifact、Attempt、Step，关联 ID 一致。 |
| EV-02 | 正常 | P0 | 业务断言失败但截图、DOM、网络证据齐全 | 机器结论为可审计 fail，失败原因引用真实证据，不被标记为“证据缺失”。 |
| EV-03 | 正常 | P1 | 核验证据完整且断言无冲突 | 确定性 Gate 给出结论；不因展示需要而调用 Judge。 |
| EV-04 | 极端 | P0 | 删除、改写或替换已提交 Artifact 内容、摘要、大小、Run/Attempt 关联 | 完整性校验和签名/根哈希失效，报告标记 integrity-invalid，finalStatus 不得为 pass。 |
| EV-05 | 极端 | P0 | 以 fixture、simulated、legacy-unverified 或跨 attempt Artifact 证明核心步骤 | 这些来源不能满足正式 Gate；缺失核心 runtime evidence 时不能 pass。 |
| EV-06 | 极端 | P0 | 需求未覆盖、核心步骤未执行，或 LLM 给出“通过”建议 | Gate 为 blocked/fail/needs-human-review；LLM 不得将机器事实升级为 pass。 |

## 14. 执行记录模板

## 15. 建议的执行顺序

1. 先执行 `PJ-*`、`RT-*`、`SEC-*`，确认被测项目和权限边界可靠。
2. 再执行 `PL-*`、`DS-*`、`RUN-*`、`EX-*`，覆盖从需求到真实执行的主链路。
3. 最后执行 `EV-*`、`JD-*`、`RP-*`、`OP-*`；其中 `EV-*` 与 `SEC-*` 的 P0 用例为发布前阻断项。
