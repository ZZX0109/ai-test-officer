# AI 测试官产品规格

版本：v0.1  
更新时间：2026-07-02  
产品定位：提交前显式灰度验收 Agent

## 1. 产品一句话

AI 测试官从 Git diff / PR / 需求出发，生成风险驱动测试 plan，接管浏览器、鼠标和键盘进行可视化分层验收，捕捉电脑画面与结构化证据，最后把可复核质量报告交给用户裁决。

## 2. 目标用户

- 独立开发者：提交前希望快速知道这次改动有没有明显风险。
- 前端/全栈开发者：希望 AI 帮忙覆盖核心页面体验、接口异常和回归路径。
- 测试同学：希望从 diff 自动生成测试计划，并得到可复核证据。
- 值班/发布负责人：希望在合并或发布前看到风险、证据和建议动作。

## 3. 核心问题

现有 AI 编程工具主要解决“怎么写代码”。但提交前更痛的是：

- 这次改动到底影响了哪些业务路径？
- 哪些路径必须测，哪些可以不测？
- 自动化测试失败时，证据是否足够复核？
- AI 的判断是否可靠，最终谁来裁决？
- 用户能不能看见 Agent 是怎么测的？

AI 测试官要解决的不是“帮我写几个测试”，而是：

> 把一次代码变更变成可视化、可追踪、可复核、可裁决的质量证据链。

## 4. MVP 输入

- `requirement_text`：需求说明或验收标准。
- `git_diff`：本次代码变更。
- `app_url`：本地被测应用地址。
- `project_path`：当前项目路径。
- `test_command`：可选，例如 `npm test`、`npm run test:e2e`。
- `user_permission_profile`：用户授权等级。

## 5. MVP 输出

- 影响范围分析。
- 风险清单。
- 显式灰度测试 plan。
- 每条测试路径的步骤、预期和证据来源。
- Live View 可视化执行过程。
- 电脑画面/窗口画面截图或录屏。
- DOM、network、console、trace、断言结果。
- 失败归因和复现步骤。
- 用户裁决建议：继续、复核、阻塞、修复后重测。

## 6. 显式灰度层级

系统内置固定灰度层级，Agent 可以建议做到哪一层，但用户拥有最终决定权。

### Level 1: `smoke`

目标：确认页面和基础能力没有明显崩坏。

检查内容：

- 页面能打开。
- 核心元素出现。
- 没有明显 console error。
- 基础接口没有 500/404。

失败策略：

- 自动重试一次。
- 仍失败则记录证据。
- 提示用户是否继续后续层级。

### Level 2: `core_path`

目标：验证本次 diff 直接影响的核心业务路径。

检查内容：

- 任务筛选。
- 订单筛选。
- 表单提交。
- 状态变更。
- 关键 API 参数和返回结果。

失败策略：

- 自动重试。
- 仍失败则继续其他测试路径。
- 最终报告标记为高风险。

### Level 3: `edge_case`

目标：验证边界和异常路径。

检查内容：

- 空状态。
- 错误输入。
- 权限不足。
- 接口失败。
- 移动端视口。
- 加载态和错误态。

### Level 4: `regression`

目标：验证历史高风险路径和相关旧用例。

检查内容：

- 相关历史测试。
- 旧 bug 复现场景。
- 与本次 diff 相邻的业务路径。

## 7. 权限模型

权限设计参考 Codex / Claude Code 的分级授权思路，避免 OpenClaw 式泛化接管风险。

| 等级 | 名称 | 能力 | 是否需要确认 |
|---|---|---|---|
| P0 | `observe` | 观察画面、读取状态、采集日志 | 默认允许 |
| P1 | `browser_control` | 操作指定浏览器窗口和被测应用 | 首次确认 |
| P2 | `workspace_control` | 读取项目文件、运行项目内测试命令 | 首次确认或按命令确认 |
| P3 | `ide_terminal_control` | 操作 IDE、终端、调试工具 | 每次确认 |
| P4 | `system_control` | 系统弹窗、跨应用操作、权限授权、删除文件、网络访问、凭据访问 | 必须显式确认 |

默认禁止：

- 读取密码、浏览器凭据、聊天记录、无关私密目录。
- 安装未经验证的第三方技能。
- 后台长期自治执行。
- 未经确认的跨应用操作。
- 未经确认的删除、提交、推送、联网请求。

## 8. 画面捕捉

画面捕捉是必选能力，用于让用户看见测试过程，并在测试后复核证据。

MVP 必须支持：

- 截取指定浏览器窗口。
- 关键步骤截图。
- 可选录屏片段。
- 记录鼠标点击坐标。
- 记录键盘输入摘要。
- 记录当前活动窗口。

画面证据不能单独作为最终判定。最终判断必须结合：

- DOM 状态。
- network 请求和响应。
- console 错误。
- trace。
- 业务断言。
- 用户裁决。

## 9. 证据冲突处理

如果画面证据和结构化证据冲突，例如截图看起来失败但 DOM 断言通过，系统进入复核流程：

1. 自动复现同一路径。
2. 对比前后两次画面和结构化证据。
3. 尝试定位原因：异步加载、视觉延迟、选择器错误、页面遮挡、接口失败。
4. 仍不确定时，生成复核包提交给用户。

## 10. 测试执行策略

执行前必须生成完整测试 plan 和详细路径。

单路径失败处理：

1. 自动重试。
2. 重试仍失败，记录证据、候选原因和复现步骤。
3. 继续执行下一个路径。
4. 全部路径结束后统一归因。

最终报告需要区分：

- 单路径失败。
- 分层灰度失败。
- 系统性失败。
- 环境失败。
- 测试脚本失败。
- 需要用户裁决的问题。

## 11. 工作台界面

推荐三栏布局：

- `Diff & Context`：Git diff、需求、PR 描述、影响范围。
- `Agent Plan & Actions`：风险清单、灰度层级、测试路径、当前操作。
- `Live Evidence`：实时画面、截图、trace、network、console、断言结果。

关键交互：

- 用户确认测试 plan。
- 用户调整灰度层级。
- 用户暂停/继续 Agent 操作。
- 用户确认高风险权限。
- 用户查看失败复现包。
- 用户给出最终裁决。

## 12. MVP Demo 场景

建议锁定任务管理系统。

核心功能：

- 任务列表。
- 状态筛选：全部 / 进行中 / 已完成。
- 新建任务。
- 空状态。
- 接口失败提示。

故意引入 bug：

- 修改状态筛选逻辑后，点击“已完成”仍显示全部任务。
- 或者前端请求漏传 `status=completed`。

这类 bug 适合演示：

- diff 能关联到筛选功能。
- Agent 能生成核心路径测试。
- 鼠标点击筛选按钮后，画面能直观看到列表错误。
- network 能证明请求参数异常。
- 报告能给出复现步骤和疑似代码位置。

## 13. 非目标

MVP 不承诺：

- 支持任意复杂仓库。
- 真实线上流量灰度。
- 自动决定是否发布。
- 完全替代人工测试。
- 任意电脑任务接管。
- 只靠截图判断业务正确性。

MVP 承诺：

- 针对一个固定 Demo 应用跑通闭环。
- 可视化执行测试路径。
- 捕捉画面和结构化证据。
- 给出可复核报告。
- 由用户最终裁决。
